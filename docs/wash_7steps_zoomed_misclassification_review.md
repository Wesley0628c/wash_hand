## 1. 結論與分析範圍

影片最後顯示 **7/7 完成，但存在分類錯誤與錯誤累積進度**。最明顯的是示範「內」時提前完成「夾」，示範「弓」時卻累積「內」，以及「大／腕」互相混淆。因此不能用完成步驟數當成辨識準確率。

本次讀取指定影片 `data/processed/wash_7steps_zoomed.mp4`（1920×1080、29.97 FPS、1147 幀、約 38.27 秒），按每秒取樣查看影片原有的 HUD、手部骨架與教學內容，並檢查目前工作目錄中的程式。影片 HUD 明示 `RULE | Win: 0.5s`。

**證據限制：**以下時間點是取樣畫面的實際顯示，不代表整段每一幀都輸出同一類。教學文字與手勢作為人工參考，轉場不強行標成某一步。未取得製作這支成品影片時的逐幀特徵、執行參數與程式版本，因此「影片已確認的錯誤」和「目前程式可造成錯誤的機制」分開說明，不宣稱已找出每一幀的唯一觸發條件。未將有 HUD 和骨架的成品重新送入模型，避免疊圖干擾而產生另一組結果。

## 3. 目前程式的判斷流程

主要入口：[test_video.py](../src/test_video.py)、[pipeline.py](../src/pipeline.py)。以下以影片使用的 rule 模式為主。

```text
影片幀
→ MediaPipe 手部偵測、CLAHE 補救
→ 左右手配對，缺失時保留最多 4 幀座標
→ 幾何／角度／跨幀形變特徵
→ 雙手規則或單手 fallback → softmax 分數
→ 依目前進度調整各類機率
→ 0.5 秒滑動平均與切換判斷
→ display_label
→ 依觀測狀態給計時權重
→ FSM 累積各類秒數、達標打勾、HUD
```

### 3.1 偵測與特徵

[hand_detector.py](../src/hand_detector.py)：MediaPipe 最多偵測兩隻手，偵測與追蹤門檻預設均為 0.50。全畫面偵測不足兩手時嘗試 CLAHE，只有手數增加才採用補救結果。右側 ROI 模式則裁切寬畫面右側 58%、垂直 5%–95%，放大兩倍；ROI 模式只在完全沒找到手時啟用補救。

左右手主要依 handedness 與前一幀手腕距離配對；短暫遺失保留原座標最多 4 幀，狀態稱為 `held`。30 FPS 下約為 0.13 秒。

[features.py](../src/features.py)：各手以手腕為原點、手腕到中指 MCP 的距離為尺度。特徵包含五指關節角度、掌心法向量、掌心距離、指尖／PIP／拇指／手腕的跨手距離、指尖散開程度、交錯深度、X 方向重疊及 `velocity`。跨手距離主要用兩手平均尺度正規化。

注意：`both_hands_detected` 只檢查兩組座標是否存在，**包含 held 座標，不等於當下真實偵測到兩手**。

### 3.2 雙手規則

[rule_classifier.py](../src/rule_classifier.py) 中的角度單位為度；距離通常為掌長正規化值。`min_curl` 是兩手各自四指平均角度中較小者；角度越大越伸直。以下概述實際條件，精確布林式以程式為準。

| 類別 | 主要條件 | 原始分數 |
|---|---|---:|
| 外 | 手軸夾角 <65、掌距 <1.30、min_curl >135、X 重疊 <0.30 | 3.2 |
| 大 | 對側掌心或拇指根部接近拇指尖（<0.85），相較指節距離有優勢，掌距 <1.20 | 3.3 |
| 夾 | 掌距 0.60–1.60、min_curl >130，且外與大未觸發；交錯深度 <1.15，或較寬鬆的次級條件 | 3.3／2.8 |
| 腕 | 指尖中心接近對側腕 <0.72，或掌心接近腕且 wrist_ratio <0.75；掌距 <2，排除很平直且軸對齊的手型 | 3.5 |
| 弓 | min_curl ≤135 或兩手彎曲差 >18；PIP 近對側掌心 <0.85，且比指尖距離不大太多；掌距 <1.50、X 重疊 <0.35 | 3.3 |
| 立 | min_curl ≥120、指尖中心近掌心 <1、指尖散開 <0.32、X 重疊 <0.35，另有掌距／指尖對 PIP 比較，且大未觸發 | 3.2 |
| 內 | 掌距 <0.65、min_curl >135，且外／弓／大／腕未觸發 | 3.4 |
| 內 fallback | 掌距 <1.50，其他洗手類都未觸發 | 2.6 |
| 其他 | 掌距 ≥1.50 且沒有洗手類成立 | 2.0 |

這不是完全獨立的加分系統：許多規則仍用前面類別的分數作為排除條件，而且多數是直接指定分數。`palm_normal_dot` 雖被讀取，實際上未用於這些分類條件。

### 3.3 單手規則

只剩一組座標時採 **if／elif 優先鏈**，依序判斷：

1. 指尖散開 ≥0.44、四指平均角 >135 → 夾。
2. 四指平均角 ≥165、拇指角 ≥140 → 內。
3. 握拳型與拇指彎曲，搭配形變或拇指尖近腕條件 → 腕。
4. 拇指尖近腕、拇指彎曲或指定形變條件，且四指角 <165 → 大。
5. 四指角 <132、拇指角 ≥115 → 弓。
6. 四指角 130–155、散開 ≤0.26 → 立。
7. 拇指角 <135、四指角 >140、散開 <0.38 → 外。
8. 第二個夾條件、四指角 >138 的內 fallback，否則其他。

單手外分支範圍比表面上窄：拇指角 <115 等情況已被前面的「大」攔走。第二個夾分支中四指角 >135 的部分也已被第一個夾分支覆蓋（恰等於 135 的邊界例外）。單手張開手指並不能證明十指交錯，握拳也不能證明正在搓對側手腕。

### 3.4 機率、平滑與進度先驗

所有類別分數經 softmax 正規化；這是規則分數轉換，不是經資料校準的正確率。例如單一類分數 3.5、其餘七類為 0，最高機率約 82.5%，並非程式註解寫的 97%。

FSM 在分類之後再調整機率：自由模式中未完成的當前類 ×1.20，已完成類 ×0.75；順序模式目標類 ×1.45、下一類 ×1.05、已完成類 ×0.70，再正規化。`FrameResult.raw_scores` 已含這層調整，不是純規則原始輸出。

[accumulator.py](../src/accumulator.py) 保留最近 0.5 秒，依新舊給約 0.7–1.0 權重平均。最高機率 <0.30 時候選為 other。換類條件是「連續候選達指定幀數 **或** 超過原鎖定類機率 0.12」，並非兩者都必須成立。pipeline 的 rule 模式固定要求 2 幀，但強差距可以直接換類。

### 3.5 計時與完成

pipeline 預設 free、每類累積 1.0 秒。`test_video.py` 同樣如此；`realtime.py` CLI 預設 hybrid、2.0 秒，不能把兩個入口混為一談。

| 目前觀測狀態 | 計時權重 |
|---|---:|
| other 或沒有任何 observed 手 | 0 |
| 雙手 observed | 1.0，沒有動作門檻 |
| observed + held，velocity ≥0.012 | 0.75 |
| observed + held，velocity <0.012 | 0.20，仍計時 |
| 單手 observed + missing，有形變，類別為夾／弓／大／立／腕 | 0.70 |
| 同上，但內／外 | 0.60 |
| 單手 observed + missing，無形變 | 0 |

[狀態機](../src/state_machine.py) 每幀增加 `observed_times[label] += dt * weight`。free 模式允許分散在整段影片的片段累積，沒有要求連續一秒，長時間中斷也不清除累積值；完成勾選永久保留到 reset。

`observed_label` 只有 weight ≥0.50 才保留動作，但 0.20 仍送入 FSM 計時。因此「可靠觀測分布」和真正計入的秒數不完全一致。既有報告所述「靜止必定零計時」與目前程式不符。

## 4. 可能造成誤判的核心邏輯

### A. 跨手 X 重疊使用不同原點，是明確的特徵設計問題

`finger_x_overlap` 比較 `left_norm` 的指尖 X 與 `right_norm` 的 MCP X 範圍；但兩手各自以自己的手腕歸零、各自縮放。這把兩手真實相對位置消掉，算到的是各自手型的投影相似性，不能代表畫面中的跨手重疊。

此值卻用來排除外、弓、立（門檻 0.30／0.35），可能錯誤封鎖正確類，再讓內 fallback 或其他類勝出。這可解釋一種「弓難以成立、內反而勝出」的路徑，但沒有原始逐幀特徵，不能斷言影片 19 秒一定由此造成。

### B. 「內」是過寬的兜底；「外」未真正驗證掌背接觸

只要兩掌距 <1.50，其他類沒有觸發，就給內 2.6 分。真正的弓若被角度、距離或 X 重疊擋住，也可能退化成內。外依賴手軸方向、伸直程度與距離，沒有使用掌面朝向作確認，掌心相對但軸近似平行也可能符合。對應影片的內→外、弓→內錯誤。

### C. 單手 fallback 把缺少的接觸證據當成已知

一隻張開的手就可能被判夾；一隻彎曲的手就可能被判腕或大。洗手時遮擋頻繁，分類會在雙手與單手分支來回切換。單手結果又可按 0.60／0.70 累積，錯誤不只出現在字幕，也會進入完成紀錄。

### D. 多個距離最小值可能來自不同手，且腕／大辨別不足

`min_tips_to_palm`、`min_knuckles_to_palm`、`min_fingertip_spread` 等各自取兩方向最小值，組合條件可能由不同手分別滿足，沒有保證「同一隻主動手」的指尖、指節與握持關係一致。腕規則亦缺乏完整的包覆位置與持續旋轉證據，容易和大競爭。影片 24、34、37 秒顯示兩者的混淆。

### E. held 座標與真實手一起進入雙手幾何

移動中的真手加上舊位置的 held 手，會形成當下不存在的接觸距離。它們和真正雙手採相同規則；降權只在分類後計時階段進行，無法防止錯誤分數污染 0.5 秒歷史。

### F. velocity 不是搓洗速度，靜態／追蹤雜訊可能被當成動作

velocity 是手腕歸零、尺度正規化後，相鄰兩幀關節座標的平均位移，未除以 dt。整隻手平移被消除，真實搓動可能很小；骨架抖動、ID 交換或重偵測跳動反而可能很大。相同動作換 FPS，數值也不同。雙手 observed 更完全不要求這項動作證據。

### G. 進度反過來干預辨識，加上零碎累積放大錯誤

某類完成後被乘 0.75，競爭類可能開始勝出，即使畫面動作未換；分類錯誤又會累積其他步驟。這是可成立的回授路徑，需要記錄先驗前後分數才能量化。影片中的提前勾選已證明「是否完成」不能代替分類評估。

### H. 平滑標籤直接拿去計時，沒有要求當前證據一致

滑動視窗在轉場保留上一動作；只要目前手還可見，舊的 display_label 仍可繼續收取時間。`other` 又混合無手、低信心與非洗手三種情況，使用者無法知道問題在哪一層。

## 5. 建議如何修改

以下是修改方案，**本次只新增分析文件與證據圖，未改動辨識程式**。門檻示例是待驗證的工程起點，並非已證實有效的新參數。

| 優先級 | 檔案 | 修改內容 | 對應問題 |
|---|---|---|---|
| P0 | features.py | 跨手重疊改用共同原點、共同尺度；再投影到穩定掌面局部軸 | 修正無效的 X 重疊，避免封鎖弓／立／外 |
| P0 | pipeline.py、state_machine.py | 分離顯示標籤與計時標籤；只讓當前證據支持的分類計時 | 防止平滑殘留與不可靠分類累積完成 |
| P0 | state_machine.py | 完成進度不再反向改變分類機率；順序資訊只用於引導 | 避免完成某步後分類偏向其他步 |
| P1 | rule_classifier.py | 收窄內 fallback；單手無接觸證據時標 uncertain，不直接確認夾／腕等 | 降低誤判與假完成 |
| P1 | features.py、rule_classifier.py | 分別建立左主動／右主動的完整接觸證據，再合併分類結果 | 避免不同手的最小值拼成不存在的姿勢 |

| P1 | features.py | 使用 dt 與共同座標計算兩手相對運動，另留關節形變特徵 | 分辨真搓動、平移與追蹤跳動 |
| P2 | accumulator.py、ui.py | 以持續秒數確認換類、限制模糊分類計時，HUD 顯示低信心／遮擋原因 | 改善抖動與回饋可理解性 |

### 5.1 修正跨手特徵

共同座標的基本形式可寫成：

```python
origin = (left_hand[0] + right_hand[0]) / 2
scale = max((left_scale + right_scale) / 2, 1e-4)
left_shared = (left_hand - origin) / scale
right_shared = (right_hand - origin) / scale
```

先在共同座標計算接觸；重疊方向改用穩定的掌寬軸，而非螢幕 X 軸，以降低畫面旋轉的影響。只改共同原點仍不能證明手指真正穿插，需結合手指交替排列、掌距及接觸位置。跨手 Z 也不應直接視為真實共同深度；在無可靠共同深度時，以影像平面接觸近似配合每手姿態，並保留不確定性。

### 5.2 重構分類規則

- 內必須有正向掌心相對與接觸證據，不能因其他類失敗就自動成立。掌面法向量只能在左右手身份與骨架品質可靠時使用。
- 外加入掌背關係；夾加入跨手手指交替關係，不能只用單手張開幅度。
- 弓／立對同一主動手比較 PIP 和指尖到被洗掌面的距離；排除「另一手較伸直」造成的 min/max 混用。
- 大／腕分別要求包覆位置落在對側拇指區／手腕區，加入短時序相對旋轉或往復證據。
- 多類近似平手時輸出 uncertain，不靠規則排列順序強迫勝出。softmax 顯示為分類分數，不稱為已校準正確率。

### 5.3 分開顯示與完成判斷

建議保留平滑結果供畫面顯示，但計時使用獨立證據閘門：

```text
當前手部品質合格
且當前分類與平滑分類一致
且該類具備必要接觸／動態證據
且分數與類間差距通過驗證後的門檻
→ 累積該類有效時間
否則 → 顯示可短暫保留，計時為 0
```

不宜把所有單手情況永久否決，否則包覆類動作會嚴重漏判；可以用近期可靠雙手接觸建立動作，再用短暫遮擋延續，但不得用單手弱證據直接建立新步驟。雙手 observed 也必須通過動態驗證，移除「低動態 observed + held 仍給 0.20」的隱性計時。

free 模式應同時保存「累積有效時間」與「當前連續證據段」。完成需達到足夠時間及最小持續性；例如先試 0.3–0.5 秒穩定段，短遮擋暫停、長中斷重置該段。具體容忍時間由驗證集選擇，不能只調到這支影片剛好 7/7。

順序模式還有額外漏洞：目前 `is_early_next` 在當前進度 ≥85% 且標籤為下一步時即可完成，沒有要求本幀 weight >0。若保留此捷徑，至少要要求下一步具備可信當前證據；較清楚的做法是完成仍需滿足原本時間。

### 5.4 加入可追查的紀錄與驗收

在原始、無疊圖影片上逐幀輸出 CSV／JSON：時間、人工標籤、兩手 observed/held、特徵、每條規則是否成立、先驗前機率、先驗後機率、平滑標籤、計時標籤、權重、實際加計秒數和完成事件。

先保存目前版本基準，再分開驗證每項修改。這支影片的驗收重點：

1. 內段不能提前完成夾；弓段不能替內增加有效秒數；腕段不能替大補足進度。
2. 分別計算逐類 precision／recall、混淆矩陣、拒判率與轉場延遲，不只看 7/7。
3. 另報每步首次完成時間、錯誤動作貢獻的計時量，以及真雙手／單手／held 各自表現。
4. 加入靜止雙手、單手張開／握拳、只做一種動作、短暫遮擋、左右手交換、畫面旋轉及不同 FPS 的回歸案例。
5. 用不同人、不同角度與不同影片做獨立驗證；不能將同片相鄰幀分散到訓練與測試後宣稱泛化改善。

優先修正共同座標、計時證據與進度先驗，再調分類門檻；否則放寬規則或縮短達標時間，可能只讓錯誤更快變成綠勾。
